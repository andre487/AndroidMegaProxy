# Проверка релиза

Регламент приёмки релиза MegaProxy. Проверяется конкретный подписанный APK-кандидат
с установленным происхождением. Зелёный CI — исходное условие, а не замена проверки
на устройствах. Debug-сборка или неизвестный checkout не заменяют релизный артефакт.

Метод основан на review 5G Proxy Client, DNS Resolver, TG WS Proxy и «Белый список?»
из рабочего каталога сопровождающего `f-droid-review`: идентификация артефакта,
обычный UID приложения, положительные и отрицательные контроли, независимые сетевые
доказательства, восстановление после ошибок и явные границы выводов. Старые
результаты других приложений ничего не доказывают для MegaProxy или новой версии ОС.

## Результаты и доказательства

Для каждого сценария **на каждом устройстве**: **PASS**, **FAIL**, **BLOCKED**,
**NOT TESTED** или **N/A**. N/A требует причины, связанной с продуктом/платформой;
отсутствие времени или оборудования — NOT TESTED. Анализ исходников и JVM-тест
не заполняют ячейку проверки на устройстве. Частичный успех описывается точно.

Запись содержит ID сценария, время UTC, commit/SHA-256 APK, устройство/сборку ОС,
предусловия, действие, ожидаемый и наблюдавшийся результат, пути к доказательствам,
вердикт и результат восстановления. Скриншот «Подключено», код возврата ADB и
наличие задания в планировщике не доказывают передачу данных. Нужен уникальный токен
запроса и сопоставление ответа обычного приложения с логом сервера или захватом.
Отрицательные проверки сети требуют работающих контролей до и после. Существенные
ошибки аутентификации и утечки повторяются минимум дважды с новыми токенами.

Сырые экспорты, ключи, личные имена профилей, идентификаторы устройств/аккаунтов и
захваты хранятся локально: каталог 0700, чувствительные файлы 0600. В Git попадают
только проверенные обезличенные записи и синтетические стенды. Не загружать APK
автоматически на VirusTotal в рамках ревью, не создавать публичные сервисы, не публиковать issues
или релизы в рамках обычного тестового прогона.

Штатный workflow выпуска по тегу отдельно сканирует публичные подписанные APK;
см. [автоматизацию релиза](release-automation.md).

## Подготовка и условия приёмки

| ID | Процедура и необходимые доказательства |
| --- | --- |
| A01 | Зафиксировать commit исходников кандидата, изменённые файлы, versionName/code каждого APK, min/target SDK, ABI, toolchain и lock-файлы. Сохранить чужие изменения. Для ветки документации отдельно указать commit собранного приложения. |
| A02 | Выполнить `bundle exec fastlane android test`, `bundle exec fastlane android python_checks` и `bundle exec fastlane android native_integration`; сохранить команды, статусы, число тестов и ссылки CI для точного коммита. `test` запускает только native/JVM/lint/build. Дополнительно обязательны обе проверки API 26/API 35: `bundle exec fastlane android device_test_build`, затем `bundle exec fastlane android device_tests api:26` и `bundle exec fastlane android device_tests api:35`, либо их полные результаты CI. Использовать ускоренную эмуляцию с холодным запуском; не перезапускать упавшие тесты ради зелёного результата. Пропуск PR-проверки по diff не доказывает покрытие кандидата; CI релизной ветки выполняет все наборы. Debug TUN/JNI и интеграция GOST/OpenSSH дополняют, но не заменяют приёмку подписанного APK. |
| A03 | Собрать `bundle exec fastlane android release_artifacts` с JDK 21 и штатной release-подписью. Сохранить SHA256SUMS, `apksigner verify --verbose --print-certs`, `aapt dump badging`, итоговые permissions/components и ABI. Не менять production versionCode ради теста обновления. |
| A04 | Сопоставить исходный и merged manifest, объяснить разрешения зависимостей. Проверить exported-компоненты, intents, FileProvider, backup, SDK, исполняемые assets, динамическую загрузку, скачивание APK, изменения зависимостей/лицензий. Сверить политику приватности и описание с поведением. |
| A05 | Для реального кандидата F-Droid закрепить recipe/upstream/fdroidserver и digest официального buildserver; выполнить metadata checks, scanner и неизменённый recipe. Где предусмотрено — официальную проверку reproducibility/signature-copy с соответствующим upstream APK. Gradle-сборка этого не заменяет. Отсутствие применимого recipe/релиза отметить явно. |
| A06 | Заново описать два телефона и два эмулятора: модель, Android/API, OEM build, patch, ABI, размер страницы памяти, экран/шрифт/язык, установленный пакет/версию/подпись, VPN/Private DNS/Always-on/lockdown, разрешения и сеть. Один эмулятор — минимальный заявленный API (сейчас 26), другой — API 35, как второй обязательный набор CI. Более новые API проверяются дополнительно. 4 KiB не доказывают поддержку 16 KiB. |
| A07 | До изменений сохранить конфигурацию приложения и системные настройки. Использовать синтетические профили и отдельные тестовые приложения; на личном телефоне направлять в VPN только их. Иметь разрешение на перезагрузку/переключение сети. Не очищать и не удалять существующую установку, не менять личный PIN. |
| A08 | Поднять контролируемые HTTP/HTTPS origins, GOST HTTPS/SOCKS5/MASQUE, OpenSSH, отдельные реквизиты/ключи jump, HTTPS-источники подписки, DoH, логи и точку захвата. Включить UDP, подготовить UDP echo/HTTP3 origins; для H12–H15 нужны TCP HTTPS и UDP MASQUE на одном числовом порту каждого узла. Подтвердить прямой контроль и исправность стенда. Loopback/ADB reverse сами по себе не доказывают физический handover или отсутствие DNS-утечек. Личные приложения через стенд не направлять. |
| A09 | Отдельно от устройств проверить доказательства релизной автоматики: все обязательные наборы успешны для точных head/base релизного PR; тег указывает на фактический merge-коммит с этими двумя родителями и деревом проверенного head. Сверить version/ABI codes и обе локали changelog. Для разрешённого выпуска по тегу сопоставить хеш каждого подписанного APK с SHA256SUMS, завершённым анализом VirusTotal, Markdown/JSON-отчётами и ссылками в релизе. Ошибки API, таймауты, malicious/suspicious блокируют публикацию. Отрицательные сценарии проверять Python-стендами, без создания живого релиза; регламент не разрешает merge/tag/publish. |

## Приоритеты при ограниченном бюджете проверки

Сначала подтвердить APK, базовую передачу данных на каждом тестовом устройстве,
отказы при неверной аутентификации/доверии, DNS/UDP/маршрутизацию с контролями,
восстановление и применимую миграцию. Восстановление личных устройств и сбор
доказательств остаются обязательными заключительными шагами. Редкие UI-комбинации,
полный перебор вариантов и длительные прогоны можно явно отложить, оставив
NOT TESTED. Сокращённый прогон не превращает невыполненные release gates в PASS.
Не начинать новый сценарий, если после него не останется времени вернуть
устройства и удалить временный доступ.

## Матрица четырёх устройств

I01–I06, P01–P07, T01–T10, C01–C05, L01–L11, D01–D05, U01–U04 и E01–E03 выполняются
на всех четырёх устройствах, где применимы; добавить S01–S04 для SOCKS5 и H01–H15
для MASQUE/предпочтения HTTP/3 в HTTPS. Варианты транспорта и узлов записывать отдельными подслучаями.
Сложные захваты, Direct Boot, forced Doze и разрушительные проверки данных сначала выполняются на выделенных эмуляторах.
На телефонах — в пределах полученного разрешения. Исключение для телефона остаётся
в матрице; результат эмулятора не подставляется вместо него.

### Установка, разрешения и интерфейс

| ID | Действия → требуемый результат |
| --- | --- |
| I01 | Чистая установка в пустой эмулятор/тестовый профиль, два холодных запуска, обход всех основных экранов/настроек. На телефонах сохранить данные. Прочитать установленный APK через `pm path` и сверить SHA-256 на каждом устройстве. |
| I02 | Обновить предыдущий подписанный релиз с синтетическими профилями до кандидата. Проверить профили, секреты, активный/Always-on профиль, routing, счётчики/настройки и источник обновления; затем реальный запрос. Сохранить идентичность обоих APK. Переустановка той же версии не является миграцией. |
| I03 | Отказать, затем выдать VPN consent; отменить подключение; безопасно отозвать consent переключением VPN. Сопоставить UI, VPN/service и трафик; старые callbacks не должны сообщать успех. При отказе уведомлений нужны понятное объяснение и путь в настройки. |
| I04 | Подключить/отключить/переподключить через UI и уведомление; быстрые повторные нажатия, Back, Home, удаление задачи, recreation и rotation. Нет второго туннеля, вечного spinner или подключения после Stop. После переходов проверять данные. |
| I05 | EN/RU, узкий экран, крупный шрифт, portrait/landscape, светлая/тёмная тема, клавиатура, внешний/внутренний экран складного телефона. Все действия доступны, длинные диалоги прокручиваются. Проверить IEC/SI, латинское MiB, лимиты, время и пустые/ошибочные состояния. |

### Профили, сохранение и доверие

| ID | Действия → требуемый результат |
| --- | --- |
| P01 | Создать/изменить/клонировать/выбрать/переставить/удалить синтетические HTTPS, HTTPS Jump, SSH, SSH Jump, SOCKS5 и MASQUE α профили; отдельно проверить предпочтение HTTP/3 в HTTPS (H12–H15); отменить черновик. Перезапустить после сохранения, проверить независимость полей и active/Always-on references. Удалять только тестовые профили. |
| P02 | Импорт URI/text/full JSON; экспорт без секретов и с явно включёнными секретами; импорт обратно и реальное подключение. Проверить отсутствующие/пустые секреты, stable ID, duplicate merge, старую/будущую schema, повреждённый/обрезанный/слишком большой файл и отмену SAF. Нет частичного разрушения данных или тихой потери секретов. Явные неизвестные JSON transport/URI scheme отклоняются без тихой замены на HTTPS; пропущенный legacy type использует HTTPS. Игнорируемые browser/неизвестные поля сообщаются однократно без значений; экспорт сверяется с vendored MegaProxyConfig. Неподдерживаемые поля не проходят round-trip. |
| P03 | Rotation/background при save/import/export; activity/process death на эмуляторе. Потерянный экспорт не должен обнулить существующий файл. Искать синтетический секрет в saved state/логах. Доступность хранилища до разблокировки и реальные отказы Keystore — отдельные проверки. |
| P04 | SSH TOFU: Cancel, независимая сверка fingerprint, Accept, повторное соединение; смена ключа сервера должна отклоняться. Отдельно jump/destination, пароль/ключ и разные реквизиты. Нет молчаливого изменения доверия или direct fallback. |
| P05 | HTTPS и, при наличии в кандидате, MASQUE α: правильная идентичность, недоверенный/self-signed и wrong-host сертификат. Исключение действует только на выбранный узел; затем вернуть проверку. Невалидный JA3 и TLS-профиль. Разрешённый self-signed стенд не доказывает CA/hostname verification. |
| P06 | Оставить редактор профиля/общих настроек открытым, обновить подписку с новыми реквизитами/маршрутизацией; сохранить только имя или одну настройку. Нетронутые свежие значения и нечитаемые зашифрованные секреты сохраняются; намеренное изменение побеждает только для своего поля. Повторить отказ записи/Retry и удаление профиля во время сохранения. Изменить SSH host/port/pin при открытом запросе доверия: принятие старого запроса не доверяет изменённому узлу. Проверить FLAG_SECURE на экранах секретов и в снимках недавних приложений. |
| P07 | На одноразовых данных эмулятора внести повреждённый JSON профилей/общих настроек, неверные типы routing-полей и недоступные секреты Keystore. Исходные байты сохраняются, ошибка понятна; маршрутизация и реквизиты не сбрасываются молча. Запуск не использует небезопасные значения по умолчанию; Stop остаётся доступен для работающего ручного VPN с учётом Always-on. Вызвать failover с повреждёнными настройками: нет падения или тихой смены профиля. Явно восстановить стенд и проверить работу. Сверить миграцию старого IPv6 с конфигурацией первого фактического соединения. |

### Передача данных, маршрутизация и диагностика

| ID | Действия → требуемый результат |
| --- | --- |
| T01 | HTTP/HTTPS из обычного приложения через GOST, OpenSSH, HTTPS Jump, SSH Jump, SOCKS5 и MASQUE α, включая оба результата выбора HTTP/3 в HTTPS (H12–H15): уникальные токены, сравнение upload/download, серверные доказательства, повторные запросы и одновременные потоки. Проверить роли узлов и отсутствие двойного подсчёта трафика. Origin отвечает только после write half-close клиента: полный ответ должен сохраниться после FIN для каждого транспорта. Отправлять данные и FIN подряд, без искусственной задержки; при отказе отдельно проверить прямой production-dialer с той же версией сервера. |
| T02 | Правильные → неверные → отсутствующие → восстановленные реквизиты каждого узла. Работающие контроли обязательны; отрицательный токен не должен успешно доходить до origin. Надпись «Подключено» при отказах не является успехом. |
| T03 | Refused/timeout/reset прокси, недоступный origin, обрезанный ответ; затем восстановление. Ограниченное ожидание, понятная ошибка, восстановление; нет direct fallback вне явно выбранной routing policy. |
| T04 | All-app routing на эмуляторе; selected-app на всех устройствах с двумя обычными UID — включённым/исключённым. Переключить local bypass, проверить контролируемые LAN/private и public адреса. Доказывать маршрутом, а не checkbox. |
| T05 | IPv4; IPv6 allow/block при независимо проверенном IPv6 uplink/origin. HTTPS через TCP (HTTP/1.1 или HTTP/2) и SSH блокируют проксируемый UDP/QUIC, кроме DNS; настроенный local bypass проверить отдельно: при работающем прямом контроле токен не должен попасть на UDP-origin. Для MASQUE α, HTTPS с выбранным HTTP/3 и SOCKS5 подтвердить передачу UDP на origin, локальный UDP-bypass и отказ для слишком больших датаграмм; отдельно проверить ограничения Chrome/Firefox и IPv6-target в GOST. HTTP/2 fallback браузера не является QUIC. См. [ограничения MASQUE](masque.md). |
| T06 | Диагностика IP/страны выхода, отказ основного провайдера и fallback; сверка с egress сервера. Отмена, offline/invalid профиль, отсутствие синтетических секретов в логе. Отказ внешнего провайдера отделять от ошибки туннеля. |
| T07 | Передать известный объём, проверить totals upload/download, reset/limit/persistence. Порог ротации SSH-сессии в MiB обновляет сессию согласно настройке; это не квота трафика и не условие отключения VPN. Selected/all failover: недоступный primary, исправный secondary, исчерпанные варианты, Stop во время failover; проверить фактический egress. |
| T08 | Проверить [TCP-метрики](connection-metrics.md) на контролируемом трафике: RTT до первого прокси, не до сайта; отсутствие данных отличается от нуля. На отдельном стенде вызвать потери, сопоставить исходящие ретрансляции с независимым захватом и проверить истечение данных через пять минут без новых замеров. Сокеты jump/multiplexing учитываются однократно; отдельная диагностика не меняет метрики, новая сессия VPN сбрасывает их. Результаты native-тестов записывать отдельно от наблюдений на устройствах. |
| T09 | Сверить логи успешного согласования HTTPS и SSH (при наличии MASQUE α — также HTTP/3, мультиплексирование и выбранный отпечаток) с контролируемым сервером: версия TLS/шифр/ALPN, фактическая версия HTTP CONNECT после fallback, начальные алгоритмы SSH в обоих направлениях. Проверить оба звена jump. В событиях не должно быть IP, доменов, реквизитов, данных владельца сертификата и полных баннеров; использовать синтетические маркеры. RTT/ретрансляции сами по себе не запускают failover; восстановление после таймаутов/сбросов проверяется отдельно. |
| T10 | Запустить «Тест» для MASQUE, SOCKS5 и HTTPS с выбранным HTTP/3: отдельно записать результаты HTTP/3 Cloudflare и BrowserLeaks. Недоступность одного/обоих не стирает успешные HTTPS/exit-IP результаты. При HTTPS fallback показать предупреждение об UDP без ложного успеха HTTP/3. Native-пробы используют проксируемый UDP без TCP fallback, но обходят Android TUN; дополнительно нужен включённый в VPN обычный браузер/приложение и контролируемый HTTP/3 origin (H06). Доступность внешних сервисов — дополнительное доказательство, не детерминированный CI gate. Во время задержанного временного «Теста» выполнить Stop/start или сменить профиль: старое завершение не останавливает новый VPN и не публикует устаревшие успех/диагностику. |

### Подписка на конфигурацию

Использовать временные HTTPS-источники и синтетические секреты. Записывать C01–C05
отдельно; ручное обновление и доставка по расписанию — разные подслучаи.

| ID | Действия → требуемый результат |
| --- | --- |
| C01 | Импортировать подписку; поставить на паузу и обновить вручную; перезапустить с просроченной проверкой. Отказ primary → рабочий backup → восстановленный primary, затем отказ всех источников. Импорт не включает VPN. При удалении удалённых профилей сохраняются корректное владение, локальные профили и существующий active/Always-on выбор. |
| C02 | Отклонить 401/403, перенаправления, неверный UTF-8, слишком большой распакованный gzip, ошибочные поля, пустой снимок и конфликт ID без замены рабочих профилей. ### MASQUE α / HTTP/3

H01–H11 проверяют явный MASQUE, H12–H15 — предпочтение HTTP/3 в HTTPS,
включая Jump, на всех четырёх устройствах.
Также повторить I01–I06, P01–P03, P06–P07, T02–T04, T06–T10, C01–C05, L01–L11, D01–D05 и
U02–U04 с MASQUE-профилем: проверки транспорта не заменяют общие фичи. Для
кандидата без конкретного режима указать N/A только для его сценариев и идентичность артефакта.

Использовать одноразовый GOST-стенд с авторизацией из [инструкции MASQUE](masque.md),
зафиксировать версию/конфигурацию, подготовить контролируемые TCP, UDP echo и HTTP/3
origins. Для положительной проверки доверия нужен доверенный сертификат на имя
сервера; для отрицательных — отдельные недоверенный/wrong-host стенды. Проверить
доступность UDP с устройства и хоста эмулятора: TCP/443 или ADB reverse этого не
доказывают. Сохранить приватные серверные логи/захваты с токенами запросов. Различать
внешний HTTP/3 до прокси и внутренний QUIC приложения до origin.

Runner для API 26/API 35 также проверяет Randomized/custom JA3, отказ и исправление
авторизации, отказ self-signed сертификата с положительным контролем явного
исключения, большие UDP-пакеты Chrome/Firefox с последующими малыми пакетами на
том же сокете, маршрутизацию по приложениям и failover по таймауту MASQUE → HTTPS
с ручным TLS JA3. Также проверяются анонимный/авторизованный SOCKS5 TCP/UDP,
предпочтение HTTPS и четыре сочетания доступности Jump. Перед одноразовыми
UDP/TCP DNS-пробами подавления AAAA проходит TCP-запрос к приватному origin:
это подтверждает готовность VPN-маршрута до UDP, но не реальное DoH-разрешение
или отсутствие утечек. Используются одноразовый GOST с авторизацией и приватный origin.
Это не заменяет проверки доверенного сертификата, DNS-захват, внутренний HTTP/3,
IPv6 uplink и физический handover ниже.

### DNS, lockdown и внешнее управление

## Актуализация регламента

До выбора сценариев зафиксировать последний коммит каждой языковой версии и
проверить все последующие коммиты кандидата (`git log BASE..CANDIDATE` и diff),
а не только changelog. Каждую фичу/исправление сопоставить с ID сценариев и
существующими JVM/Go/device-тестами; пробелы оставить явными. Дополнительно сверить
полный текущий набор фичей: возможность могла появиться до BASE, но не попасть
в регламент. Разделять автоматические доказательства и вердикты подписанного APK
на устройствах, включая skipped-наборы и ограничения стенда. Сохранять ID сценариев
и датированные исторические отчёты; обновлять обе локали вместе. Автоматический
release workflow проверяет CI и публикует после тега; эту ручную матрицу он не
собирает и не делает обязательным автоматическим условием.

## Ошибки, исправления и решение о релизе

Воспроизвести ошибку на неизменённом кандидате и сохранить доказательства: серьёзность,
устройства, шаги, expected/actual, контроли, предполагаемый слой и уверенность.
Не объявлять платформенную проблему ошибкой приложения без доказательств. Опасный
участок кода исследуется и без runtime-воспроизведения; такой вывод помечается
как результат анализа исходников.

Регламент/отчёт и исправления — разные PR. Для исправления создать отдельную ветку
от актуального main или worktree. Сначала регрессионный тест, падающий до исправления,
затем минимальное исправление причины. Парсеры/состояния/форматы — JVM; UI — имеющиеся
Robolectric-тесты; native transport — Go; совместимость серверов — `native_integration`;
системная маршрутизация/lifecycle — существующий CI на эмуляторах API 26/35 и локальные
устройства. Обязательный hosted CI должен оставаться детерминированным; физические
сети, OEM и длительные прогоны проверяются локально. Повторить воспроизведение и соседние сценарии на затронутых
устройствах, указать новый commit/APK. Старый FAIL не превращается в PASS без retest.

Не рекомендовать релиз при необъяснённых падениях, потере данных, обходе доверия/
аутентификации, неверной подписи/ABI, неработающем основном туннеле на поддерживаемом
устройстве или непроверенной обязательной миграции/lockdown. Блокировка критического
пункта означает **РЕЛИЗ НЕ ПРОВЕРЕН**, а не «всё хорошо». Явно перечислить платформенные
ограничения и пробелы. Публикация — отдельное действие пользователя.

Отчёт: `docs/reviews/release-YYYY-MM-DD.md`: кандидат/артефакты, четыре устройства,
матрица, находки по функциям, ссылки retest, решение о релизе и путь к локальным
доказательствам. Старые отчёты остаются датированными снимками; при изменении продукта
или методики обновляется этот регламент.
