## Confirmed failure: GOST final bytes lost on write half-close

**T01 fails against official GOST3.3.0.** An ordinary included app writes a unique
17-byte body and immediately calls `shutdownOutput`; the origin reads until EOF
and echoes the complete body. Several GOST transports deliver zero bytes instead.
HTTP/HTTPS request success does not cover this stream boundary.

The same immediate-FIN failure reproduces with the production MASQUE dialer directly
on the host, without Android TUN. GOST3.3.0 embeds `github.com/go-gost/x v0.16.0`;
its `internal/net/pipe.go:pipeHalf` handles a read error before writing bytes returned
by that same read. `(n > 0, io.EOF)` therefore discards the final data.

A diagnostic build of the same GOST sources, with only the write-before-error order
corrected, passes the immediate-FIN production-dialer check. A separate250ms delay
also avoids the symptom, but is **not a client fix**. These diagnostic passes do not
replace the official-server failure. Existing native
`TestMASQUEHalfCloseThroughProductionWrappers` already covers consecutive Write /
CloseWrite with a correctly implemented server.

No client workaround or personal-server change was applied. Release acceptance
remains blocked by the official-server failure and the unexecuted gates below.

## Decision

The shortened review confirms core traffic, authentication rejection, subscriptions
and bounded recovery on this signed API35 candidate. It does **not** approve a
release: T01 has a reproduced GOST-server failure, SOCKS5 UDP and controlled browser
HTTP/3 are inconclusive, and deferred rows remain open. No client workaround,
upstream server publication, personal proxy change, merge, tag or release upload was
performed. Both language versions of the procedure now require immediate FIN with
no artificial delay and direct production-dialer isolation on failure.
